# `fixtures/` — the golden corpus

**The rule: fixtures are trimmed, sanitised, and provenanced. A full-page
capture is rejected in review.**

This corpus is what lets six pipeline stages be tested exhaustively without a
browser, without a network, and without a review source. Every case is a
directory containing three files.

| File            | What it is                                                                             |
| --------------- | -------------------------------------------------------------------------------------- |
| `page.html`     | The captured markup, **trimmed to the review container subtree plus minimal ancestry** |
| `meta.json`     | Provenance: selector pack version, capture date, locale, what the case exercises       |
| `expected.json` | Golden extraction output, **generated by the engine**, never hand-written              |

## Capture

Use `scripts/capture-fixture.mjs`. It trims and then pipes through
`scripts/sanitize-html.mjs`, which strips scripts, tokens, cookies, tracking
attributes, and inline event handlers.

**Review text and author names are retained.** They are needed for parser
correctness and are already public. Stripping them would produce a corpus that
tests the shape of the markup and nothing about the extraction it exists to
verify.

## Why trimming is a rule and not a preference

A full-page capture is roughly a megabyte of someone else's application markup
per case. Twenty of those makes the repository large, makes every diff
unreviewable, makes the sanitiser's job unverifiable by eye, and captures far
more third-party content than the test needs. The subtree is the part under
test; the rest is noise with a licensing question attached.

## Why `expected.json` is generated

A hand-written golden file asserts what someone _believed_ the engine produces.
When it disagrees with reality, the natural response is to edit the golden file
until the test is green — which converts a regression suite into a
transcription exercise. Generating it means a diff in `expected.json` is always
a real behavioural change and always deserves the review it gets.

## Pack pinning

`meta.json` pins the selector pack the case was captured under, and the case
keeps being tested against **that** pack. This is what proves the corpus tests
extraction rather than today's markup, and it is why old packs are retained
indefinitely.

## Coverage the corpus must keep

Twenty DOM cases spanning the ordinary path, locale and script variation
(RTL, CJK, emoji, German and Hindi relative dates), missing and anonymous data,
rating-only reviews, owner replies, truncation, and the 5,000-review cap — plus
five adversarial cases that must assert _correct failure_: a stalled partial
load, changed structure, a challenge page, a consent interstitial, and markup
embedded in review text.

The last of those, `019-markup-in-review-text`, is a security test. It exists to
prove that normalisation removes markup rather than escaping it, on the path
that reaches every client website.

Specified by TRD §6.7 and §61. TR-TEST-011, TR-TEST-012.
